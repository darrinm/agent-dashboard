§1Summary

Agent sessions now outnumber the places you look for them. They're spread across Ghostty tabs, background Claude sessions, Codex Desktop, VS Code and claude.ai, and none of those surfaces tell you when an agent stops and waits for you. Work stalls silently.

Agent Tower has two parts. A collector reads what Claude Code and Codex already write to disk and turns it into one list of sessions, each with a state you can trust. A native menu bar app shows that list, notifies you when something needs you, and takes you straight into the session. A hub, added later, brings in sessions from other machines and the cloud.

Nothing here requires changes to either tool. Every signal used below was confirmed on this Mac on Sep 10, 2026, except where §17 lists it as open.

  • Another session stopped on a model refusal on Aug 20 and hasn't moved since.

§3Goals and non-goals

Goals

  • Answer “does anything need me?” from the menu bar icon, without clicking.
  • Show a correct state for every session. A false “waiting on you” costs more than a missing one, because it teaches you to ignore the icon.
  • Get from any session row to the place you can act on it in one click.
  • Cover Claude Code and Codex: this Mac first, then other machines and the cloud.
  • Cost nearly nothing to run: under 1% CPU at idle, and no transcript content leaves the machine unless you turn that on.

Non-goals

  • A transcript viewer or chat client. Rows link out to the real session.
  • Starting new agents, in the first version.
  • App Store distribution, or a UI for Windows or Linux. Linux machines get a collector in the hub phase, not an app.
  • Dollar cost tracking. Token counts are shown; pricing can come later.

§4Experience

The mockup shows the panel with sample session names and messages. One correction to it: rows should show how long a session has been in its current state, not how long ago it started (see §8).

Menu bar icon

The icon is a count plus a 3×3 grid of dots, one dot per active session. Active means working, waiting or error. Dots are ordered error first, then waiting, then working, and show the first 9.

IconStateRule
Quiet Nothing working, waiting or in error. Dim dots stand for idle and finished sessions.
Working At least one session working, none waiting. Cyan dots breathe.
2 Waiting on you The count is the number of sessions waiting or in error. Amber dots blink slowly.
1 Error Any session in error turns the count red, even when others are only waiting.

Panel

The header shows the waiting count, the longest wait, and a count per source: This Mac, Remote Control and Cloud. A source whose adapter is failing turns grey and says why. Below the header come four sections:

  • Waiting on you. Sessions in waiting or error, most recent first, because you still remember the context of fresh ones. Sessions waiting more than 7 days fold into a Stale group with a Stop all action. Today that group would hold all 6.
  • Working. Sessions in working, each with a live activity trace, plus any collision warning (§12).
  • Elsewhere. Counts and top names for Remote Control and cloud sessions.
  • Finished. Background sessions that finished in the last 24 hours.

Each row shows the state dot, name, tool and tags on the first line, and repo and branch or worktree on the second. The third line holds what the session is asking, or its last message, clamped to two lines; expanding a row shows the full text and its actions. The right edge shows time in the current state, or the activity trace for working sessions.

Notifications

  • Notify when a session enters waiting or error, once it has stayed there 20 seconds. Agents often ask and then carry on after an auto-approval.
  • Notify when a background session finishes. Interactive sessions don't notify on finish by default; that's a setting.
  • If more than 3 sessions change within a minute, send one summary notification instead of one each.
  • Notification actions: Attach and Snooze 1 hour. The same state never notifies twice. macOS Focus modes apply automatically.

Keyboard

⌥ Space opens and closes the panel from anywhere, and the shortcut can be changed. Typing filters sessions, arrow keys move between them, Return expands one, ⌘ Return runs its primary action, and Esc closes the panel.

Data only moves one way. Adapters read the sources, the state engine decides each session's state, and the store keeps current sessions plus a history of state changes. The app is a view of the store: it never reads Claude or Codex files itself.

Decision

The collector is its own process, not part of the app.

The same binary runs headless on other machines, can be tested without a UI, and can feed a web dashboard later. It does mean two pieces instead of one, so the app bundles the collector and registers it as a login item. You still install one thing.

Decision

Write the collector in TypeScript on Bun, compiled with bun build --compile into a single binary.

It runs on macOS and Linux, has SQLite built in, and handles JSONL naturally. A Swift collector inside the app was rejected because it wouldn't run on Linux machines.

§7Session model

Every adapter produces the same shape. Fields an adapter can't fill stay empty; nothing is guessed.

type State = "working" | "waiting" | "error" | "idle" | "finished" | "offline" | "unknown";

interface Session {
  key: string;              // "claude:<sessionId>" or "codex:<threadId>"
  tool: "claude" | "codex";
  origin: "local" | "remote-control" | "cloud";
  machine: string;          // "studio.local"
  name: string;
  kind: "interactive" | "background" | "desktop" | "ide" | "subagent" | "cloud-task";
  cwd?: string;
  repo?: string;
  branch?: string;
  worktree?: string;

  state: State;
  stateSince: string;       // time of the turn that caused this state
  lastActivityAt: string;
  ask?: { text: string; options?: string[] };  // what it's waiting for
  lastMessage?: string;     // at most 280 characters, code blocks removed
  error?: { kind: string; detail?: string };

  model?: string;
  tokens?: { input: number; output: number; cached: number };
  parentKey?: string;       // Codex subagents, Claude background tasks
  pr?: { number: number; url: string };
  links: { attach?: string[]; web?: string; transcriptPath?: string };

  aliases: string[];        // bridgeSessionId and similar, for merging duplicates
  provenance: Partial<Record<keyof Session, SourceId>>;  // which adapter set each field
}

§8State engine

State is the product. The engine combines every signal it has into one state per session and records when that state began.

StateMeaningClaude Code signalCodex signal
workingModel or tools are runningagents state working, or session busytask_started with no later task_complete or turn_aborted
waitingCan't continue without youagents state blocked, or a Notification hook for a permission promptPending approval: signal not yet known (Q3)
errorStopped on a failureAssistant entry with isApiErrorMessage: true, or a system entry such as model_refusal_no_fallbackturn_aborted not caused by you (Q4)
idleYour turn in an interactive session, nothing pendingInteractive session, idleInteractive thread after task_complete
finishedBackground work is doneagents state doneExec run, subagent or cloud task complete
offlineRemote machine unreachableNo heartbeat from its collector for 2 minutes
unknownNo adapter can tellShown grey, never counted in the icon

Rules

  • Precedence. When sources disagree: hook events beat CLI state, CLI state beats transcript inference, and transcript inference beats file timestamps. Within a tier, the newer signal wins.
  • When a state began. stateSince is the time of the last user or assistant turn, ignoring bookkeeping entries. One session has an informational system entry on Aug 24, so the naive last timestamp says it has waited 17 days. Its last real turn was the refusal on Aug 20, 21 days ago.
  • Hold time. A session must stay in waiting or error for 20 seconds before the icon count or a notification changes. Working shows immediately.
  • Idle doesn't count. Idle interactive sessions are listed but never add to the count. Whether they should is Q6.

§9Collector

  • Process. One binary, tower-collector. On a Mac it ships inside the app and runs as a login item; on Linux it runs as a systemd user service.
  • Watching. File-system events on ~/.claude/sessions, ~/.claude/projects, ~/.codex/sessions and Codex's database log file. It only tails transcripts that belong to live sessions or changed in the last 7 days.
  • Tailing. It saves a byte offset per file and reads only the last 512 KB the first time it sees a file. That matters: one active transcript here is 55 MB, ~/.claude/projects totals 2.4 GB and ~/.codex/sessions 1.2 GB. Nothing is ever parsed in full.
  • Codex database. Opened read-only and never written. Busy errors are retried. The schema is checked on startup; an unexpected one marks the adapter unhealthy instead of crashing.
  • Store. Current sessions live in memory. State changes go to a local SQLite file kept for 14 days, which drives the Finished section, stale detection and the success measures in §16.
  • Local API. Listens on 127.0.0.1 only, on a random port. The port and a bearer token are written to ~/Library/Application Support/Agent Tower/collector.json, readable only by you.
GET  /v1/sessions                         // current list
GET  /v1/events                           // server-sent events: session changed, removed
POST /v1/sessions/:key/actions/:action    // attach, stop, respawn, reply
POST /v1/hooks/claude                     // from the Claude hook script
POST /v1/hooks/codex                      // from the Codex notify wrapper
GET  /v1/health                           // adapter status and versions

Budget. Under 1% CPU at idle and under 80 MB of memory. A change backed by a hook shows in the app within 1 second; anything else within 3 seconds.

§10Menu bar app

Decision

AppKit status item and floating panel, both hosting SwiftUI views. Not SwiftUI's MenuBarExtra.

The icon animates, and ⌥ Space has to open the panel. MenuBarExtra has had no public way to open it from code (true through macOS 15; recheck on 26, Q7).

  • Target: macOS 26 only, using its glass effect with no fallback. Xcode 26.6 is installed.
  • Hotkey: Carbon's RegisterEventHotKey, which doesn't need Accessibility permission.
  • Notifications: UNUserNotificationCenter with Attach and Snooze actions.
  • Opening sessions: a new Ghostty window running the attach or resume command. The exact invocation is Q5.
  • Distribution: not sandboxed, because it launches the Claude and Codex CLIs and the collector reads their folders. Signed with a Developer ID; notarized only if shared.
  • Reduced motion: the dots stop animating and the count stays.
  • Settings: hotkey, which events notify, whether idle sessions show, stale threshold, hub on or off, and whether message text is shown.

§11Hooks and notify

Polling can tell a session is blocked, but only hooks know the moment it happens. Both integrations edit settings files that belong to other tools, so setup shows the exact change and asks before writing it.

Claude Code

Setup adds entries for Notification, Stop, SessionStart and SessionEnd to ~/.claude/settings.json. They sit next to your existing Notification, Stop, UserPromptSubmit and WorktreeRemove hooks. The hook script forwards the event JSON to the collector with a 1-second timeout, prints nothing and always exits 0, so it can never slow or block a session. Removing Agent Tower removes only its own entries.

Codex

Codex's notify setting takes one command, and yours is already used by Codex Computer Use. Setup replaces it with a wrapper that runs the original command first, with the same arguments, then posts to the collector. Removing Agent Tower puts the original line back.

§12Collisions

  • Version 1, same checkout. Warn when two or more working sessions share a working tree root, from git rev-parse --show-toplevel. Separate worktrees of one repo don't count; keeping agents apart is what worktrees are for.
  • Version 2, same file. Claude's file-history-delta entries record each edited file (trackingPath plus realParentDir), and Codex's patch tool calls name their files. Warn when two sessions edit the same file within 30 minutes.

§13Other machines and cloud

  • Hub. A Cloudflare Worker with one Durable Object per account. Each collector connects over a WebSocket with its own machine token. The web view sits behind Cloudflare Access.
  • What's sent. Session summaries (the model in §7 minus local file paths) and a heartbeat every 30 seconds. A machine goes offline after 2 minutes without one.
  • Merging duplicates. A local Claude session's bridgeSessionId matches its Remote Control and claude.ai id. Matches merge into one row marked local.
  • Codex Cloud. The collector on your main Mac polls codex cloud list --json using your existing Codex login. The hub never holds OpenAI credentials.
  • Claude cloud and Remote Control. No CLI returns the account-wide list. Until one exists (Q1), these sessions appear only when repo-level hooks in .claude/settings.json report them, which depends on Q2. The Elsewhere section says plainly what it can't see.

§14Privacy and security

  • Until the hub milestone, nothing leaves the machine.
  • The hub is opt-in. It receives names, states, repo, branch and token counts. Message text is off by default for the hub.
  • The local API accepts only loopback connections that present the token.
  • Stopping or replying to a session always takes an explicit click, and stopping asks for confirmation. Remote actions through the hub wait until M4 and get their own permission.
  • Agent Tower never writes to Claude or Codex data. Its only edits to their files are the settings changes in §11, made with your consent.

§16Milestones

Durations are rough estimates. Each milestone ends when its exit criteria are met, not on a date.

  1. M0Collector spike 1–2 days

    Adapters for claude agents, Claude session files and transcripts, and Codex's database and rollout files. Prints the session list and logs every state change for a day.

    Exit: spot checks through that day match reality for every session, and stateSince is right for all 6 blocked sessions.

  2. M1Menu bar app about 1 week

    Icon, panel, notifications, Attach in Ghostty, search, ⌥ Space, and the bundled collector.

    Exit: a week of daily use in which no session waits more than 24 hours without you knowing.

  3. M2Accuracy about 1 week

    Claude hooks, the Codex notify wrapper, error detection, same-checkout collisions, and the Stale group with Stop all.

    Exit: fewer than 1 in 20 “waiting” notifications marked as false.

  4. M3Hub

    Collectors on other machines, Codex Cloud, duplicate merging through bridge ids, offline states.

    Exit: a session on a second machine shows in the menu bar within 5 seconds of changing state.

  5. M4Actions and depth

    Replying to Codex via codex queue, same-file collisions, token trends, subagent trees.

Measure of success: blocked sessions older than 24 hours go from 6 today to zero and stay there.

§17Open questions

  1. Is there an API or CLI that returns the account-wide Claude session list, including Remote Control and cloud sessions?
  2. Do Claude cloud sessions run project hooks, and can they reach the hub from their sandbox?
  3. How does Codex signal a pending approval? No approval events appear in the last 30 days of rollout files here, because approvals go through auto-review, so this needs a deliberate test.
  4. Does turn_aborted say whether you interrupted the turn or it failed?
  5. What is the exact Ghostty invocation to open a new window running a command?
  6. Should idle interactive sessions count toward the icon? Proposal: no. List them in a quiet Idle group.
  7. Can MenuBarExtra on macOS 26 be opened from code? If so, revisit the decision in §10.
  8. For stale sessions, should Agent Tower offer to stop them automatically after some number of days, or only suggest it?
